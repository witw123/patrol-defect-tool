# 巡检缺陷命名分类工具：原生桌面化设计说明

## 1. 目标

将当前单文件 HTML 工具改造成 Windows 原生桌面软件，保持离线运行和本地文件处理能力，同时解决浏览器文件授权、超大图片渲染、复杂状态集中在一个脚本中的问题。

本方案明确不使用：

- Electron、Chromium、WebView、HTML、CSS、JavaScript UI
- 浏览器 File System Access API
- 浏览器 `localStorage`、IndexedDB 作为业务存储
- 为旧版本保留兼容层、迁移脚本或 fallback

目标产品是一个可安装、可卸载、可生成快捷方式、可由 Windows 文件关联启动的桌面应用。

## 2. 推荐技术方案

### 2.1 技术栈

| 层 | 选择 | 原因 |
|---|---|---|
| UI | C# + .NET 8 + WinUI 3 | Windows 原生桌面体验，支持现代窗口、菜单、对话框和高 DPI |
| 图片显示 | WinUI `Canvas` / `WriteableBitmap`，必要时使用 `Win2D` | 支持缩放、平移、矩形标注和硬件加速 |
| 文件系统 | .NET `System.IO` + Windows Storage API | 原生访问目录，不需要浏览器授权 |
| 图片编解码 | Windows Imaging Component（WIC） | Windows 系统原生，支持常见照片格式 |
| Excel 词典 | `ClosedXML` | 读取项目内 `.xlsx`，不要求用户安装 Office |
| 配置与数据库 | SQLite + `Microsoft.Data.Sqlite` | 保存项目、浏览进度、标注、结论和操作记录 |
| 日志 | `Microsoft.Extensions.Logging` | 统一记录异常和批处理过程 |
| 安装 | MSIX | Windows 原生安装、卸载、快捷方式和升级机制 |

WinUI 3 是 Windows 原生 UI 框架；它不是网页壳。UI、窗口、文件对话框和控件均由 Windows 应用框架创建。

### 2.2 为什么不选 Electron

Electron 会随应用携带 Chromium 和 Node.js 运行时，安装包、内存占用和进程数量都明显高于本项目需要。当前工具的核心工作是目录、图片和本地结果文件处理，不需要网页运行时，因此 Electron 不符合本项目的产品约束。

### 2.3 为什么不选纯 C++ Win32

纯 Win32 可以做到更底层，但目录树、数据绑定、命令状态、DPI、键盘操作和设置页面需要大量基础设施。对本工具而言，`C# + WinUI 3` 已经是原生桌面方案中开发成本和可维护性更平衡的选择。图片处理中的性能热点仍可局部使用原生 Windows API，不需要整个项目改写为 C++。

## 3. 总体架构

采用四层结构：

```text
巡检缺陷工具.exe
├─ PatrolDefect.App                 WinUI 3 窗口、页面、交互
├─ PatrolDefect.Application         用例、命令、校验、进度
├─ PatrolDefect.Domain              目录模型、照片、缺陷、结论
└─ PatrolDefect.Infrastructure      文件系统、SQLite、WIC、Excel、日志
```

依赖方向只能由上到下：

```text
App -> Application -> Domain
App -> Infrastructure
Application -> Infrastructure 抽象接口
Infrastructure -> Domain
```

业务层不直接依赖 WinUI 控件；这样后续可以独立测试目录解析、命名规则和成果归档。

## 4. 核心模块

### 4.1 项目与目录模块

负责：

- 选择并打开照片根目录
- 选择缺陷成果输出目录
- 扫描线路、杆塔、照片层级
- 生成稳定的相对路径 ID
- 监听目录变化并按需重新扫描
- 执行线路、杆塔、照片重命名

原 HTML 中的 `showDirectoryPicker`、目录句柄保存和浏览器授权逻辑全部删除。原生程序直接使用绝对路径，并在项目数据库中记录路径。

### 4.2 照片浏览模块

负责：

- 上一张、下一张、筛选后翻页
- 图片缩放、适应窗口、平移
- 后台预解码前后相邻照片
- LRU 图片缓存
- 显示原图分辨率和质量状态

图片加载必须使用异步任务，UI 线程只负责提交显示结果。禁止把完整原图长期复制到多个 UI 控件中。

### 4.3 标注模块

标注数据建议使用归一化坐标：

```text
x = left / imageWidth
y = top / imageHeight
w = width / imageWidth
h = height / imageHeight
```

这样窗口缩放、DPI 变化和重新加载图片不会破坏标注位置。

最小模型：

```text
DefectMark
├─ Id
├─ PhotoId
├─ X, Y, Width, Height
├─ Component
├─ DefectTag
├─ Conclusion
├─ CreatedAt
└─ UpdatedAt
```

保存成果时由基础照片生成圈示图，再按命名规则写入输出目录。原图始终保留，覆盖和删除前必须完成业务校验。

### 4.4 缺陷分类与归档模块

提供：

- “全绝缘缺陷”
- “其它缺陷”
- 圈示图与原图分别归档
- 批处理进度、成功数、失败数
- 失败文件清单和重试入口

批处理不直接操作 UI 控件，使用 `IProgress<BatchProgress>` 回传进度。

### 4.5 词典模块

启动项目时读取 `常规配电缺陷描述.xlsx`，转换成内存词典。词典数据不写入 UI 代码，部件、缺陷标签和分类规则由领域服务提供。

Excel 只作为初始数据源；用户编辑后的项目配置保存到 SQLite。若后续不再需要运行时编辑 Excel，可将词典导入数据库后移除 Excel 依赖。

### 4.6 状态与结论模块

照片结论固定为：

- 待检查
- 确认无缺陷
- 发现缺陷
- 需复核
- 图片不可用

所有统计从数据库查询或由应用层状态计算，不再使用散落的全局变量和 `localStorage` 键。

## 5. 界面设计

主窗口保持当前工具已验证的三栏工作流，但改成原生控件：

```text
┌─────────────────────────────────────────────────────────┐
│ 菜单栏 / 工具栏 / 项目路径 / 进度                         │
├──────────────┬──────────────────────────┬───────────────┤
│ 线路和杆塔树  │ 原图 + 标注画布            │ 缺陷信息面板   │
│ 筛选与统计    │ 缩放、平移、翻页           │ 标签、结论、保存 │
└──────────────┴──────────────────────────┴───────────────┘
```

使用 WinUI `NavigationView`、`TreeView`、`CommandBar`、`InfoBar`、`ContentDialog` 和自定义图片画布。辅助设置放在菜单和设置页，不抢占主工作区。

必须保留的交互：

- `A` / `D` / 方向键翻图
- `F` / 空格保存
- `C` 定位最后一张已看照片
- 鼠标侧键翻图
- 左侧目录自动展开当前杆塔
- 右键菜单重命名和批量操作
- 批处理时显示明确进度和可取消状态

## 6. 数据设计

建议数据库文件放在：

```text
项目目录\.patrol-defect\project.db
```

核心表：

```text
Project
Photo
DefectMark
PhotoConclusion
ViewedPhoto
DictionaryItem
OperationLog
```

`Photo.RelativePath` 是照片唯一业务键，不使用文件名作为唯一键，避免不同杆塔下的同名照片串号。

数据库只保存索引、业务状态和标注；原始照片与成果照片仍保存在用户选择的目录中，不复制进数据库。

## 7. 从现有 HTML 的迁移映射

| 现有能力 | 原生实现 |
|---|---|
| 递归扫描目录 | `Directory.EnumerateFiles` |
| 浏览器句柄 | 项目配置中的绝对路径 |
| `localStorage` | SQLite 的 Project/Settings 数据 |
| IndexedDB 目录句柄 | 删除，不再需要 |
| Canvas 双层绘制 | 原生图片画布 + 标注层 |
| 图片预加载 | `Channel` + 后台解码任务 + LRU |
| manifest JSON | SQLite `Photo` 和成果映射表 |
| 自定义弹窗 | `ContentDialog` |
| 键盘事件监听 | WinUI `KeyboardAccelerator` |
| File System Access API | .NET 文件系统 API |

现有 HTML 不建议继续作为运行时依赖。迁移时提取业务规则和命名规则，重新实现 UI 与文件操作。

## 8. 分阶段实施

### 阶段一：最小端到端版本

完成一个可运行闭环：

1. 创建 WinUI 3 桌面项目和解决方案分层
2. 选择照片目录和输出目录
3. 扫描并显示线路、杆塔、照片
4. 显示一张原图
5. 画一个矩形标注
6. 选择部件和缺陷标签
7. 保存圈示图、原图和数据库记录

### 阶段二：日常效率

加入翻图快捷键、目录树联动、结论状态、筛选、已看进度、图片缓存和预加载。

### 阶段三：成果处理

加入全绝缘/其它缺陷分类、批量归档、成果目录检查、重命名、失败重试和操作日志。

### 阶段四：发布质量

加入崩溃日志、项目恢复、异常文件提示、安装包、版本信息、签名和离线安装测试。

每个阶段都应有可运行版本，不等待所有旧功能迁移完成后才首次运行。

## 9. 性能与可靠性要求

- UI 线程不得递归扫描目录、解码大图或批量复制文件。
- 图片缓存按内存预算淘汰，默认不缓存无限数量原图。
- 写文件采用临时文件写入成功后再替换目标文件。
- 批处理逐文件记录结果，单个坏文件不应中断整个任务。
- 所有文件操作记录相对路径和异常原因。
- 窗口关闭时取消后台任务并等待写盘结束。
- 目标显示器支持 Windows 高 DPI 和窗口缩放。

## 11. 验收标准

首个可交付版本至少满足：

- 无网络、无浏览器、无 Office 也能启动
- 能打开现有巡检照片目录
- 能正确区分线路、杆塔和相对路径
- 能显示大图并缩放、平移
- 能创建、修改、取消一个缺陷标注
- 能保存成果并在数据库中恢复
- 重启程序后能恢复项目、已看进度和结论
- 同名照片不会互相覆盖或串统计
- 批量分类失败时能指出具体文件
- 可通过 MSIX 安装和卸载

## 12. 最终建议

直接新建 `PatrolDefect.sln`，以 `C# + .NET 8 + WinUI 3` 重写运行时，不把现有 HTML 嵌入新程序。先完成“打开目录 -> 浏览图片 -> 标注 -> 保存成果 -> 重启恢复”的最小闭环，再迁移批量分类、重命名和高级设置。这样得到的是原生 Windows 软件，而不是换了外壳的网页。
